# 06 — Sistema de Inteligencia Artificial — Ollama

## ¿Qué es Ollama y por qué se eligió?

Ollama es una herramienta que permite correr modelos de IA de código abierto localmente, dentro de Docker, sin necesidad de conexión a internet y sin costo por petición.

Comparación con las alternativas:

| Opción | Ventaja | Desventaja |
|--------|---------|------------|
| **OpenAI API** | Modelos muy potentes | Costo por token, datos salen de tu infraestructura, dependencia de terceros |
| **Hugging Face** | Gratuito, muchos modelos | Configuración compleja, requiere GPU para buenos resultados |
| **Ollama** | Simple, gratis, corre en Docker, privado | Modelos más pequeños, requiere RAM local |

Para Nexo, Ollama es la elección correcta: los dos modelos que usa caben en ~670MB de RAM, corren en cualquier máquina de desarrollo, y la privacidad de los datos de los negocios colombianos se mantiene en la infraestructura propia.

---

## Los dos modelos y para qué sirve cada uno

### `nomic-embed-text` (~270MB)

Este modelo convierte texto en **embeddings**: representaciones matemáticas del significado de un texto como un vector de 768 números.

Piénsalo como un mapa de significados. Cada texto tiene coordenadas en un espacio de 768 dimensiones. Los textos con significado similar quedan cerca en ese espacio, los diferentes quedan lejos:

```
"corte de cabello"  ←→  "peluquería"     : MUY cercanos (mismo concepto)
"fisioterapia"      ←→  "rehabilitación" : cercanos (mismo campo)
"corte de cabello"  ←→  "pizza"          : muy lejanos (sin relación)
```

En Nexo se usa para:
1. **Indexar tiendas**: al crear/actualizar una tienda, se genera su embedding y se guarda en `stores.embedding`
2. **Buscar en el chatbot**: se genera el embedding de la búsqueda del usuario y se compara contra los embeddings de las tiendas

### `qwen2.5:0.5b` (~400MB)

Un **LLM** (Large Language Model) pequeño: entiende lenguaje natural y genera respuestas coherentes. El `0.5b` significa 500 millones de parámetros — pequeño para un LLM, pero suficiente para las dos tareas específicas de Nexo.

Sus limitaciones: memoria de contexto corta, razonamiento limitado en preguntas complejas. Por eso en Nexo se usa solo para tareas muy acotadas con instrucciones muy explícitas, no para conversación libre.

## Cómo arranca el contenedor de IA

El `ai-service/entrypoint.sh` hace dos cosas al iniciar:

```bash
#!/bin/bash
ollama serve &       # Arranca el servidor de Ollama en segundo plano
sleep 5              # Espera a que esté listo para aceptar peticiones
ollama pull nomic-embed-text   # Descarga el modelo si no está en el volumen
ollama pull qwen2.5:0.5b       # Descarga el modelo si no está en el volumen
wait                 # Mantiene el proceso vivo
```

Los modelos se descargan en el volumen Docker `ollama_models`. La primera vez tarda ~5 minutos. Las siguientes veces, si el volumen persiste, arrancan en segundos porque los modelos ya están en disco.

## Cómo funciona la búsqueda semántica — paso a paso

Ejemplo real: el usuario escribe **"quiero acicalarme en Bogotá"**

### Paso 1 — Normalización de intención (qwen)

qwen recibe el mensaje y extrae parámetros de búsqueda en JSON:

```
Entrada: "quiero acicalarme en Bogotá"
Salida:  {
  "searchText": "arreglo personal corte cabello",
  "city": "bogotá",
  "maxPrice": null,
  "isAppointmentRelated": true
}
```

"Acicalarme" no aparece en ninguna descripción de tienda, pero qwen entiende que significa arreglarse, y lo normaliza a términos que sí aparecen en los servicios del catálogo.

Si `isAppointmentRelated` es `false` (ej: "cuánto es 2+2"), el flujo para aquí con una respuesta canned.

### Paso 2 — Embedding de la búsqueda (nomic-embed-text)

```
Entrada: "arreglo personal corte cabello"
Salida:  [0.0234, -0.1823, 0.4521, ..., 0.3341]  ← vector de 768 números
```

### Paso 3 — Similitud coseno contra tiendas (Node.js)

El backend obtiene todas las tiendas activas con embedding (`WHERE embedding IS NOT NULL`), filtra por ciudad si se detectó (`ILIKE '%bogotá%'`), y calcula la similitud coseno entre el embedding de la búsqueda y el embedding de cada tienda.

### Paso 4 — Umbral de relevancia

Solo las tiendas con `score >= 0.60` pasan. Las que no alcanzan el umbral se descartan sin mostrar al usuario.

**Si ninguna pasa:** se retorna `buildNotFoundMessage()` directamente, qwen no se llama, `stores: []`.

**Si hay tiendas que pasan:** se toman las top 3 por score, se filtran sus servicios por `maxPrice` si aplica, y se llama a qwen para redactar la respuesta.

### Paso 5 — Generación de respuesta natural (qwen)

qwen recibe únicamente los datos reales de las tiendas filtradas con instrucciones estrictas:

```
STRICT RULES:
1. Usa SOLO la información de las tiendas en DATA.
2. NO inventes nombres, servicios, precios ni detalles.
3. Responde en español amigable, máximo 2-3 oraciones.
4. Menciona nombres de tiendas y al menos un servicio con precio.
5. Invita al usuario a visitar el perfil para agendar.
```

## Similitud coseno — sin fórmulas matemáticas

Imagina dos personas de pie en el mismo punto, cada una apuntando en una dirección diferente con el brazo extendido. La similitud coseno mide el ángulo entre esas dos direcciones:

```
Misma dirección exacta  → score  1.0  (idénticos en significado)
Ángulo recto (90°)      → score  0.0  (sin relación)
Direcciones opuestas    → score -1.0  (significados opuestos)
```

Dos textos sobre peluquería apuntan aproximadamente en la misma dirección en el espacio de 768 dimensiones. Un texto sobre fisioterapia apunta en una dirección diferente. Un texto sobre videojuegos apunta en una dirección completamente diferente.

### El umbral 0.60 — calibrado con mediciones reales

Este valor no es arbitrario. Se determinó midiendo scores reales con los datos del seed:

| Consulta | Tienda | Score | ¿Pasa el umbral? |
|----------|--------|-------|-----------------|
| "corte de cabello" | Salón Valentina | **0.7633** | ✅ Sí |
| "fisioterapia" | Dr. Martínez Fisioterapia | **0.6628** | ✅ Sí |
| "fisioterapia" | Salón Valentina | **0.4648** | ❌ No (correcto) |
| "reparación celular" | TechFix Reparaciones | **>0.60** | ✅ Sí |
| "xbox 360" | cualquier tienda | máx **0.5839** | ❌ No (correcto) |
| "pizza" | cualquier tienda | máx **~0.50** | ❌ No (correcto) |

El umbral de 0.60 crea una separación clara entre búsquedas relevantes (que superan 0.62+) e irrelevantes (que quedan por debajo de 0.59). Si en el futuro se agregan nuevas categorías de tiendas y el umbral necesita ajuste, modificar `SIMILARITY_THRESHOLD` en `backend/src/services/chat.service.js`.

## Por qué el chatbot no alucina

Los LLMs tienen tendencia a "alucinar": inventar información que suena plausible pero es falsa. Para un sistema de reservas esto sería catastrófico — mostrar tiendas que no existen, precios incorrectos, o servicios inventados.

Nexo previene esto en tres capas:

1. **Umbral estricto**: si ninguna tienda es genuinamente similar a la búsqueda (score < 0.60), qwen no se llama. El mensaje de "no encontré nada" es texto hardcodeado — imposible de alucinar.

2. **Datos reales como contexto**: cuando qwen sí se llama, recibe únicamente los datos verificados de la base de datos. No puede inventar tiendas porque solo tiene datos de tiendas reales.

3. **Instrucciones explícitas**: el prompt incluye "Do NOT invent, add or assume any store name, service, price or detail not present in DATA." El modelo pequeño (`0.5b`) tiende a seguir instrucciones explícitas más fielmente que razonar libremente.

## Limitaciones y mejoras futuras

**Limitaciones actuales:**
- `qwen2.5:0.5b` puede fallar con mensajes muy coloquiales o ambiguos en dialectos regionales colombianos
- El cálculo de similitud coseno en Node.js no escala bien a miles de tiendas — requeriría `pgvector` para hacer la búsqueda directamente en PostgreSQL
- Los embeddings de las tiendas no se regeneran automáticamente cuando el emprendedor actualiza su descripción o servicios

**Mejoras posibles:**
- Cambiar a `llama3.2:3b` para mejor razonamiento (requiere más RAM)
- Trigger de PostgreSQL para regenerar el embedding cuando se actualiza una tienda
- Implementar `pgvector` para búsqueda vectorial indexada en la DB

## Consideraciones de producción

Los modelos de IA requieren memoria RAM para cargarse y mantenerse activos:

| Modelo | RAM aproximada |
|--------|---------------|
| `nomic-embed-text` | ~270MB |
| `qwen2.5:0.5b` | ~400MB |
| Sistema operativo + Ollama | ~300MB |
| **Total** | **~970MB** |

Una EC2 t2.micro tiene 1GB de RAM. Con los modelos cargados queda ~30MB libres, lo que es suficiente para el servidor Ollama pero nada más. Por eso `ai-service` necesita su propia EC2 separada del frontend y backend.

En la primera petición después del arranque, Ollama carga el modelo desde disco a RAM. Esto tarda 5–10 segundos. Las peticiones siguientes usan el modelo ya cargado: ~1–3 segundos por petición.
